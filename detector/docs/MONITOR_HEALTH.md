# 运营监测健康

监测执行成功表示取得可用证据，不表示被测接口质量良好。一个完成的低分报告属于有效检测；401、403、核心探针未完成、超时或其他执行错误不属于有效检测，也不得进入公共评分。

`monitor-once` 先执行原有的核心探针，不额外增加一次预检。出现鉴权错误后停止其他探针与补充首字延迟请求；并行阶段发现鉴权错误时取消剩余任务。已经发出的请求可能仍由上游计费。

## 状态与重试

- 退出码 `0`：取得有效证据，包括发现协议异常的低分报告。
- 退出码 `1`：鉴权失败、证据不足或执行失败。
- 退出码 `2`：配置或健康记录存储不可用。
- 退出码 `75`：冷却中或同一任务已有进程执行；没有发起重复请求，不生成新检测报告。

鉴权/配置失败从 6 小时开始退避，其他失败从 15 分钟开始退避，每次加倍，最长 24 小时。定时器仍按原配置触发；冷却到期不会自行创建后台进程或立即调用上游。成功后清零连续失败。状态保存在报告根目录的 `.monitor_health/`，使用目标锁和原子替换，文件权限为 0600；不保存 Key、Key 指纹、原始错误和上游响应。

旧报告可直接重建健康视图和冷却时间，只读取来源为运营监测且审核通过的记录，最多回溯最近 5,000 份。历史任务记录不等于当前启用的定时器清单；超过回溯上限时明确提示统计可能不完整。

## 查看与恢复

在管理员/审核员的站点管理页顶部打开“监测健康”（`/console/relays/monitoring`）。显示最近有效检测、最近采样、连续未完成次数、错误分类与冷却时间。公开模型观测页只展示汇总，不泄露目标配置或密钥。

仅本机读取状态，不执行检测：

```bash
gewu monitor-health --output-root /opt/gewu-detector/web_data/jobs
```

先检查专用 Key 是否可用、是否对应正确的入口与模型权限。不要仅因 401 就认定上游故障或模型造假。配置修复后可等待原定时任务；如确需提前复测，在原有 `monitor-once` 命令末尾显式添加 `--retry-now`。这个选项会调用上游并可能消耗额度，不能作为无人值守的重试循环。

私有健康 API 为 `GET /api/status/monitor-health/summary`，使用 `X-Gewu-Internal-Token`，未配置令牌也拒绝访问。路径兼容现有 nginx 转发规则。健康视图最多缓存 60 秒；健康状态无法读取时明确显示未知，不显示绿色成功。
